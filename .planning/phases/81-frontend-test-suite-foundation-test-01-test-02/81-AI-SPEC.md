## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Developer Tooling

**User Population:** Developers

**Stakes Level:** Medium

**Output Consequence:** Test results determine if code is merged or rejected.

### What Domain Experts Evaluate Against

Dimension: Test Reliability
Good (expert accepts): Tests run consistently and pass/fail deterministically in both local and CI environments.
Bad (expert flags): Tests are flaky, intermittently failing in CI despite passing locally, or failing due to race conditions.
Stakes: High
Source: Frontend developer consensus — flaky tests destroy trust in the test suite and slow down velocity.

Dimension: Environment Fidelity
Good (expert accepts): The test environment accurately simulates the required browser APIs.
Bad (expert flags): Tests pass but the component crashes in a real browser because it relies on inaccurate mock APIs.
Stakes: High
Source: Testing library maintainers — over-mocking leads to false positives.

Dimension: Performance & Speed
Good (expert accepts): Test suite executes quickly (milliseconds per test) and provides immediate feedback during watch mode.
Bad (expert flags): Test suite takes minutes to run, blocking developers from iterating quickly.
Stakes: Medium
Source: Developer productivity studies — slow feedback loops break developer flow state.

### Known Failure Modes in This Domain

1. **False Positives:** Tests pass because they assert on implementation details rather than user-facing behavior, missing actual regressions.
2. **JSDOM Limitations:** Layout-dependent code fails because JSDOM does not render visually.
3. **CI/CD Environment Mismatch:** Tests pass locally but fail in CI due to missing dependencies or timing issues.
4. **Memory Leaks:** JSDOM instances are not properly destroyed between test runs, leading to out-of-memory errors in large test suites.

## 3. Framework Quick Reference

> Fetched from official docs by `gsd-ai-researcher`. Distilled for this specific use case.

### Installation
```bash
npm install -D vitest jsdom @testing-library/dom
```

### Core Imports
```javascript
import { describe, it, expect, beforeEach, afterEach } from 'vitest';
```

### Entry Point Pattern
```javascript
import { describe, it, expect } from 'vitest';

describe('UI Component Test', () => {
  it('should render correctly in jsdom environment', () => {
    document.body.innerHTML = '<div>Hello World</div>';
    const div = document.querySelector('div');
    expect(div.textContent).toBe('Hello World');
  });
});
```

### Key Abstractions
<!-- Framework-specific concepts the developer must understand before coding -->
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| Vitest Environment | JSDOM provides a mock browser environment | For testing code that relies on DOM APIs (document, window) |
| Describe/It Blocks | Test suites and test cases | Organizing and executing tests |
| Expect/Matchers | Assertions | Verifying expected outcomes |

### Common Pitfalls
<!-- Gotchas specific to this framework and system type — from docs, issues, and community reports -->
1. Forgetting to set the environment to 'jsdom' in the Vitest configuration, leading to 'document is not defined' errors.
2. Relying on actual browser layouts or styles; JSDOM doesn't render visually, so `clientHeight`/`clientWidth` will not work.
3. Not cleaning up the DOM after tests; mutations to `document.body` persist between tests in the same file unless explicitly cleaned up.

### Recommended Project Structure
```
project/
├── vitest.config.js       # Framework configuration (environment, setup files)
├── tests/
│   ├── setup.js           # Setup file (e.g., importing jest-dom matchers)
│   └── components/
│       └── ui.test.js     # Test files matching *.test.js or *.spec.js
```
